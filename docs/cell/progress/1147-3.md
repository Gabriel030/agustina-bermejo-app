# 1147 pieza 3 (T22.8a) — identity/usecase/person: transacciones al compositor

## Criterios de aceptación
- [x] `ChangeOwnPasswordService`, `UpdateNotificationPreferencesService`, `UpdateOwnProfileService` y `UploadAvatarService` sin `@Transactional`
- [x] Un compositor por caso de uso en `identity/service`: `OwnPasswordChangeTransaction`, `NotificationPreferencesUpdateTransaction`, `OwnProfileUpdateTransaction`, `AvatarUploadTransaction`
- [x] Cambio de clave y revocación de sesiones siguen atómicos; el perfil no queda con dos commits; el archivo del avatar se borra si la transacción revierte
- [x] Tests de límite transaccional no transaccionales con sabotaje verificado (`PersonTransactionBoundaryIT`)
- [x] Entradas de las cuatro clases fuera de las líneas congeladas de R10 y de use cases

## Notas
- Se eligió compositor para los cuatro: ninguno hace una sola escritura a través de un especialista. Contraseña: guardar + revocar sesiones + auditoría. Perfil: pedido de cambio de email por token + documento + dirección. Avatar: archivo + persona + limpieza ligada a la transacción. Preferencias: varias altas y bajas.
- Los compositores resuelven la persona actual dentro de su transacción (`CurrentPersonService`), así el caso de uso no toca entidades.
- `OwnProfileUpdateTransaction` recibe `UpdateOwnProfileRequest` (paquete `dto`, no depende de `usecase`): no hay ciclo service/usecase y se evitan 13 parámetros posicionales del mismo tipo. Los demás reciben primitivos.
- `UpdateOwnProfileUseCase` sigue devolviendo `Person`: quedan las dos entradas "has return type Person" del baseline de use cases (sin cambio de contrato).
- Sabotaje: sin `@Transactional` en `OwnPasswordChangeTransaction` y `OwnProfileUpdateTransaction` fallan los dos tests del IT; restaurado.
