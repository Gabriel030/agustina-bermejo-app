# #1196 T#2b-1 — Envío de la invitación a un destinatario

## Criterios de aceptación
- [x] Revalida bajo lock (oleada y destinatario `findByIdForUpdate`): oleada RUNNING y destinatario PENDING/QUEUED; si no, `NOT_SENDABLE` sin enviar
- [x] Ya activó => `ACTIVATED`; inactivo/no ALUMNO/no encontrado => `EXCLUDED NOT_ELIGIBLE`; sin mail => `EXCLUDED NO_EMAIL`
- [x] Token solo en memoria, emitido al enviar; nunca en tablas ni logs (test que busca el token en todas las tablas y en los logs; sabotaje verificado)
- [x] Link `${app.frontend.base-url}/activar?token=`; el token del mail canjea en `POST /auth/activate`
- [x] Mail por `TransactionalEmailGateway` con CB y bulkhead `mail`; CB/bulkhead abierto => `DEFERRED` sin consumir intento ni dejar delivery
- [x] 4xx => `PROVIDER_REJECTED`; 5xx/timeout => `PROVIDER_UNAVAILABLE`; fallo de token => `TOKEN_ISSUE_FAILED`
- [x] Categoría `INVITATION` (migraciones V442/V443), una `NotificationDelivery` por intento con dedupKey `INVITATION:{wave}:{person}:{intento}`
- [x] Cupo global (INVITATION suma a los transaccionales del tope diario) y `daily_cap` de la oleada: sin cupo => `NO_QUOTA`
- [x] `retryFailedInvitations(waveId)`: FAILED -> QUEUED con cupo, RUNNING y `app.invitation-wave.max-attempts` (default 3)
- [x] Doble invocación concurrente => un solo mail

## Notas
- El token se emite en una transacción `REQUIRES_NEW` (`InvitationActivationTokenRequester`): las excepciones de dominio del emisor no contaminan la transacción del envío.
- Si el canal de mail se cierra durante la llamada, `InvitationSendDeferredException` revierte el intento y el use case devuelve `DEFERRED`. El token ya emitido (commit propio) invalida el anterior; nadie recibió el nuevo enlace, la persona se vuelve a invitar en el siguiente intento.
- El envío de INVITATION no pasa por `VerifiedEmailRequiredPolicy`; ningún job de despacho existente levanta la categoría.
- ITs sin contextos nuevos: `InvitationSendIT` usa el contexto base y arma el compositor con un gateway de test.
