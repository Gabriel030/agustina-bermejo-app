### T#1 — Token de activación
- Valor observable: después de este PR, una persona con token válido canjea el enlace y fija su contraseña.
- Cómo probarlo: test de integración del canje; token vencido, usado y reemitido (invalida el anterior).
- Tests esperados: vencido, reusado, invalidado por reenvío, hash en DB (nunca el token), rate limit, el canje setea password, `emailVerified` y `grantSystemAccess`.
- Notas de diseño: patrón de `PasswordResetCodeIssuer`/`EmailVerificationSender` (hash SHA-256, vencimiento, evento); token URL-safe de 32 bytes; sin contraseñas generadas.
- Formato de salida esperado: PR + checklist en `docs/cell/progress/1196-1.md`.
- FUERA DE ALCANCE: oleadas, mails, pantalla.
- Criterios de aceptación verificables: ver tests; sin enumeración de usuarios en `/auth/activate`.
- Comando de verificación: `./mvnw test -Dtest='identity.**,ArchitectureTest,ModularityTest'`

### T#2 — Oleada y despacho
- Valor observable: después de este PR, una oleada RUNNING envía a lo sumo `batchSize` mails por tanda, respeta ritmo y tope, y no envía fuera de oleada.
- Cómo probarlo: test del job con gateway falso y reloj controlado.
- Tests esperados: máximo N por tanda, ritmo, tope diario sumado a la categoría, pausa/reanudación, excluidos (sin mail, ya activo, no importada) con motivo, revalidación al enviar (si activó entre medio, pasa a ACTIVATED y no se envía), no se envía fuera de una oleada RUNNING, concurrencia (`findByIdForUpdate`, unique `(wave_id, person_id)`, dedupKey por oleada/persona/intento).
- Notas de diseño: tablas propias, `NotificationDelivery` con categoría `INVITATION`, job propio con `@SchedulerLock`; no pasar por `VerifiedEmailRequiredPolicy`.
- Formato de salida esperado: PR + `docs/cell/progress/1196-2.md`.
- FUERA DE ALCANCE: endpoints HTTP, webhook de Brevo, front.
- Criterios de aceptación verificables: los tests de arriba pasan; sabotaje del límite N cae.
- Comando de verificación: `./mvnw test -Dtest='notification.**,ArchitectureTest,ModularityTest,QualityRulesTest'`
